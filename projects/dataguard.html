The problem

Two databases can disagree quietly.

A source system and its reporting replica can diverge without a single dramatic failure. Missing rows, duplicate records, null changes, timestamp drift, and changed values can all affect downstream reporting. DataGuard was built to find those differences, classify them, and leave evidence someone can investigate. The core-banking scenario and faults used here are simulated.

Architecture

Check cheaply. Investigate precisely.

Both datasets enter the same comparison path. Detailed row hashing is reserved for partitions flagged by cheaper checks.

Key decisions

Why it works this way.

01

Gate the expensive work

Partition-level checks run first. Row hashing runs only when a partition looks suspicious, avoiding unnecessary detailed comparisons.

02

Classify the difference

A mismatch should be actionable. DataGuard distinguishes fault types so someone investigating a problem knows what kind of drift occurred.

03

Separate engine and insights

DataGuard Core handles reconciliation. DataGuard Insights provides the BI layer for exploring trends and risks through a separate deployed dashboard.

What broke

Three bugs that changed the design.

The useful lessons came from testing the cases where the first implementation failed.

Hashing ran too early

Row hashing was not gated by the cheaper partition checks. The first version was slower than the naive baseline. Fix: run detailed hashing only for suspicious partitions.

Null drift was missed

The partition suspicion check ignored null-count drift. Recall fell to 77% for one fault type. Fix: include null-count differences when deciding which partitions need deeper inspection.

Duplicates looked missing

Duplicate rows were incorrectly classified as missing rows. Fix: correct the classification logic so the reported fault matches the evidence.

Limitations

What remains unfinished.

PARTITION_ANOMALY classification

The documented PARTITION_ANOMALY fault type is not implemented. DataGuard classifies seven of the eight documented fault types. The banking scenario is simulated, so the benchmark and injected-fault results should be understood in that test environment.
